# ADR-004: Kafka, доставка, идемпотентность и сверка провайдера

Дата: 2026-11-08. Статус: принято.

## Контекст

БД и Kafka не коммитятся одной транзакцией. После успешного платежа или выдачи ответ может потеряться. Повтор без прежнего ключа способен создать второй эффект. У банковского API окно идемпотентности ограничено; хранение события в DLT не означает бизнес-отказ.

## Варианты

| Вариант | Преимущества | Ограничения |
| --- | --- | --- |
| Отправить сообщение после commit без outbox | Мало таблиц | Падение между commit и публикацией теряет событие |
| Рассчитывать на exactly-once транспорт | Простое объяснение | Не покрывает HTTP, физическое оборудование и банковский API |
| Outbox/inbox, бизнес-ключи и сверка | Восстановление после повторов и неизвестных исходов | Дополнительные записи, фоновые задачи и временная несогласованность |

## Решение

Выбрать Kafka с отдельным топиком на тип бизнес-события и независимой consumer group каждого сервиса. Ключ записи — `rental_id`. Для учебного стенда фиксируются три партиции, одна реплика и семь суток хранения; эта конфигурация не резервирует единственный диск брокера. Порядок гарантирован только внутри партиции одного топика, поэтому версии ресурсов остаются обязательными.

Изменение агрегата и outbox записываются одной локальной транзакцией. Издатель повторяет публикацию с тем же `event_id`, использует `acks=all` и `enable.idempotence=true`, а outbox помечает опубликованным после подтверждения Kafka. Идемпотентный producer не заменяет бизнес-дедупликацию после перезапуска или повторной публикации outbox.

Получатель атомарно записывает уникальное `(consumer, event_id)`, применяет локальный эффект либо ставит сверку и только затем фиксирует следующий Kafka offset. Собственный исходящий факт входит в ту же транзакцию БД. Автоматический commit offsets отключён. Обработка партиции последовательна: нельзя зафиксировать позицию дальше ещё неготовой записи. Падение между commit БД и commit offset вызывает безопасное повторное чтение.

Kafka не переносит ошибочные сообщения в DLT автоматически. После пяти попыток обработчик сохраняет отдельную ошибку и задание DLT в одной транзакции; после неё исходный offset можно зафиксировать. Публикатор отправляет исходные key/value и координаты записи в DLT-топик сервиса. Ошибка не помечается успешно применённой в обычном inbox, чтобы разрешённый оператором повтор после исправления причины мог обработаться. При недоступности БД партиция приостанавливается без commit и без DLT.

HTTP-сверка дополняет события. При исчерпании Kafka retention автоматическое пропускание записей отключено: выполняются сверка по авторитетным API и восстановление из сохранённых журналов/outbox, после чего позиция чтения устанавливается явно. Результаты банка и физических действий не зависят от вечного хранения Kafka-топика.

HTTP-идемпотентность различает ключ запроса и бизнес-ключ. Новый клиентский ключ не обходит уникальность активной аренды, назначения устройства и начисления периода. Сохраняются отпечатки запросов; несовпадение параметров — конфликт. Ресурсы и ключи в учебной версии не удаляются; поздняя команда не должна пережить удалённый tombstone.

Начисление, попытка оплаты и операция провайдера имеют разные идентификаторы. Внутри начисления допускается лишь одна неразрешённая попытка. Подтверждённый отказ позволяет создать новую, `UNKNOWN` — нет. Ключ, тело и время первой отправки сохраняются до обращения к провайдеру. Возврат аналогично имеет свой постоянный ключ и уникальность на начисление.

ЮKassa использует окно идемпотентности 24 часа. В его пределах повторяется исходный запрос, после него неизвестная операция создания не повторяется вслепую. Известный ID сверяется через `GET`; неустановимый исход требует разбирательства. Проверенное банковское уведомление и polling сходятся к одному локальному переходу через сравнение версии/блокировку. Местный факт `UNKNOWN` нельзя заменить `DECLINED` только по таймеру.

События содержат полный снимок и версию своего агрегата. Версии разных сервисов или разных ресурсов несравнимы. Независимый факт возврата не отбрасывается по более новой версии операции выдачи. Авторитетные факты и исходные данные сохраняются даже при конфликте проекций.

## Последствия

Доставка может повторяться, но бизнес-эффекты защищены локальными ограничениями, устойчивыми ключами и протоколом участника. Обещание относится к этим условиям, а не к магическому exactly-once для всей сети. Бесконечная недоступность или утрата всех журналов не гарантируют автоматического завершения.

Нужны наблюдение за backlog и неизвестными операциями, очистка по отдельной будущей политике и ручная сверка редких неустановимых банковских результатов. Правила окна провайдера нельзя заменить вечным кэшем только в Billing.
