# ADR-001: границы сервисов и независимость отказов

Дата: 2026-11-08. Статус: принято.

## Контекст

Аренда пауэрбанка соединяет физическую выдачу/возврат и списания с карты. Возврат должен приниматься при недоступности финансовой подсистемы, включая её БД; пользователь не должен продолжать аренду только из-за неисправности Billing. Уже зарегистрированные финансовые обязательства должны обрабатываться при остановке Rentals. Контроллер принимает устройство без доступа к облачной БД.

## Варианты

| Вариант | Преимущества | Ограничения |
| --- | --- | --- |
| Модульный монолит с одной БД и адаптерами | Проще разработка и локальные транзакции | Общий отказ приложения/БД затрагивает аренды и расчёты; банковская и аппаратная распределённость всё равно остаётся |
| Rentals вместе с Billing, отдельный Stations | Меньше внутренних сетевых вызовов | Финансовое хранилище остаётся общей причиной недоступности центрального закрытия аренды |
| Rentals, Billing, Stations с независимыми хранилищами | Изоляция выбранных отказов, самостоятельные процессы восстановления | Больше инфраструктуры, событий, сверок и временно разных представлений |

## Решение

Выделить три сервиса по [карте контекстов](../01-context-map.md). Каждый владеет своей БД и обеспечивает собственные локальные ограничения. Не считать API и worker разными бизнес-сервисами. Платёжный провайдер и контроллеры оборудования — внешние системы; их адаптеры находятся внутри Billing и Stations.

Для выбранной изоляции проектировать независимые экземпляры PostgreSQL. Возврат закрывается одной транзакцией Rentals с outbox без запроса к Billing. Финансовое закрытие может произойти позже. Billing сохраняет способы оплаты, тарифы и обязательства, необходимые для выполнения уже известных операций без синхронного вызова Rentals; жизненный цикл сверяется после восстановления связи.

Выбранные сервисные границы не являются математически обязательными. Различие таблиц, денежные данные сами по себе или наличие платёжного API не доказывают необходимость отдельного сервиса. Решение опирается на конкретную независимость отказов, проверяемую остановкой Billing вместе с его БД.

## Последствия

Потеря Billing не блокирует физический возврат и центральное закрытие аренды при доступных Rentals и Stations. Потеря Rentals задерживает его закрытие, но не уничтожает факт на стороне оборудования/Stations. Общая неисправность сети или хоста всё ещё может затронуть несколько компонентов.

Исчезает единая SQL-транзакция аренды и расчёта. Нужны протоколы восстановления, наблюдаемость и честное отображение незавершённых финансов. Для небольшого продукта без принятого требования изоляции объединение Rentals и Billing осталось бы разумной альтернативой.
